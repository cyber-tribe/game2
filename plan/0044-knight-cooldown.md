# 0044 knight-cooldown

## 背景

「game2 第4回 敵対的検証」への応答で、ユーザーから「現在の1試合を
実際に時間軸で計測して、どのフェーズが何秒なのか分析することを
最優先にします」との指摘があり、`Simulation`を実際に動かして
フェーズ別のタイムラインを計測した（放置プレイヤー——敵AIのみが
自律行動する条件）。

結果、「開拓→繁栄→初接触→小競り合い→神介入→災害→復興/逆転→
最終戦」というドラマ曲線のうち、**「繁栄」「復興/逆転」がほぼ
存在せず**、0:30〜1:00の間に発展・接触・災害・決着がほぼ同時に
起きていることが分かった。特に具体的な機械的原因として、
`knightify`で騎士化された敵のリーダーが、防御力判定なしに家を
無条件で焼き払う（`combat.ts`の`isKnight`分岐）にもかかわらず、
`knightTargetingSystem`が家を焼くたびに即座に次の最寄りの敵へ
再ターゲットするため、**無防備な陣営の集落を1体の騎士が20〜30秒
程度で壊滅させてしまう**ことが判明した。この「復興/逆転」の余地を
物理的に奪うほど速い焼き討ちが、2分決着の中心的な要因のひとつ。

## アプローチ

`combat.ts`の`createHouseCaptureSystem`で、騎士が家を焼き払った
直後に新しい`KnightCooldown`コンポーネント（`remaining`秒数）を
その騎士に付与するようにした。`knightTargetingSystem`は
`KnightCooldown`を持つ騎士への新規ターゲット割り当てをスキップする
——結果として騎士は焼き討ち後`KNIGHT_BURN_COOLDOWN`（6秒）休んで
から次の相手を探しに行くようになる。新設の`knightCooldownSystem`が
毎ティック`remaining`を減らし、0以下になったらコンポーネントを
外す。

`Walker`インターフェース自体にフィールドを追加する案は、
`world.add(entity, Walker, {...})`の呼び出し箇所がテストを含め
30箇所以上あり変更コストが大きいため避けた。代わりに騎士が焼き討ち
した直後にだけ付与される独立コンポーネントとして実装し、既存の
`Walker`の形は一切変更していない。

休憩中でも、たまたま隣接位置に来た敵ウォーカー/家との接触
（`walkerCombatSystem`/`createHouseCaptureSystem`自体）は妨げない
——`KnightCooldown`が止めるのは「次の獲物を自発的に探しに行く」
判断だけで、応戦・応焼自体は変わらない。

## テスト

- `src/game/systems/knight.test.ts`：`KnightCooldown`中の騎士へは
  新規ターゲットが割り当てられないこと、`knightCooldownSystem`が
  `remaining`を正しく減算し、0以下でコンポーネントを外すことを検証。
- `src/game/systems/combat.test.ts`：騎士が家を焼いた直後に
  `KnightCooldown { remaining: KNIGHT_BURN_COOLDOWN }`が付与される
  ことを検証。
- `npm run typecheck` / `npm run test -- --run`（234件）/
  `npm run build`がすべて成功。
- 放置シナリオ（敵AIのみで自律運転）を20回試行し、決着時間を比較：
  - 導入前（`plan/0043`の旧地形での計測値）：平均108.8秒
  - 導入後：平均137.5秒、中央値約113〜114秒、範囲49〜378秒
    （分布の裾が大きく伸び、多くの試行で明確に長引くように
    なったが、典型的なケースはまだ2分前後で決着している）。

## 残作業

この修正だけでは「2分決着」問題は解決しない。分布の中央値は
まだ2分弱で、`plan/0043`に記載した他の要因（人口増加速度、
敵AIの地形編集ペース、Armageddon発動の人口比閾値）が引き続き
支配的である可能性が高い。次にどれへ着手するかは、ユーザーが
別途示した優先順位（64×64化とゲームテンポ→城vs拡張のトレード
オフ→…）を踏まえて判断する。
