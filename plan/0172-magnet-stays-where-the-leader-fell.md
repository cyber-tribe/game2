# 0172 magnet-stays-where-the-leader-fell

## 攻略の「ポイント」欄をまだ読んでいなかった

攻略資料の面ごとの記述には4つの欄がある——インフォメーション（10項目の○×）、
使用可能神技、敵の神技、そして**ポイント**。前の3つは
`docs/original-maps.md` に全48面ぶん転記してあるが、**4つ目は手つかず**
だった。必要になるたびに拾い読みしていただけで、突き合わせていない。

16ページを取得して48面ぶんの「ポイント」を抜き出し、機構の記述を探した。
最初に出てきたのがこれである。

## マグネットはリーダーが倒れた場所に残る

No.1 は戦法として**手順そのもの**を書いている。

> (3)敵ウォーカーが平地沿いに陣地を広げ、マグネットに触れてリーダーが出来るのを待つ。
> (4)この間にマナが貯まっているので、敵リーダーに対して火柱を数回仕掛ける。
> (5)敵リーダーが焼死すると、**マグネットがその場に残る。**
> (6)別の敵ウォーカーがマグネットに触れ、リーダーになるまで待つ。

別の面が、同じことを逆の側から書いている。

> この島には敵リーダーもいるため、これを倒すと**その場に敵のマグネットが残り**、
> 別の島にいた敵が全体マップでも判るほどの速さでこのマグネットに向かってきます。

game2 は**この半分だけを実装していた**。`hero.ts` は変身のときに
`shrinePosition` をリーダーが立っていた場所へ移す（「変身するとマグネットが
リーダーのいた場所へ移動する」、`plan/archived/0146`）。**死は同じ出来事の
別の顔**であり、そちらは無かった。

結果、敵リーダーを倒しても相手の集結地は元の場所に残ったままで、攻略が
説明している戦法——**相手のマグネットを開けた土地へ引きずり出し、寄って
くる者を順に潰す**——が成立しなかった。

## 位置は覚えておくしかない

死んだと分かる時点で、エンティティはもう無い。`Position` も一緒に消えている。
なので毎tick、生きているリーダーの立ち位置を控えておき、死んだらその控えを
使う。`createLeaderLossSystem` は既に死と変身を見分けているので、そこに足した
——見分けを二度書く理由が無い。

**変身では動かさない。** 動かすのは `hero.ts` の仕事であり、ここが二重に
動かすと、変身したヒーローが歩いたぶんだけ集結地がずれる。

## この変更に含めなかったこと

「ポイント」から読み取れた、**同じ場面の別の2つ**は入れていない。どちらも
単独で評価できる変更であり、混ぜない。

- **マグネットに触れた者がリーダーになる。** game2 の `leaderSystem` は
  「集結」か「集結シンボルへ」の間しか昇格させない。攻略 No.1 の敵は
  **陣地を広げているだけ**でリーダーが出来ている（(3)）。原作の規則は
  命令に依らないように読める。
- **リーダーを失った勢力はマグネットへ向かう。** 「別の島にいた敵が全体
  マップでも判るほどの速さでこのマグネットに向かってきます」。これは
  勢力の命令そのものを上書きする話で、影響が大きい。

## 検証

- `npm run typecheck` / `npm run build` パス、テスト1050件パス（+3）。
- `leaderLoss.test.ts` 3件——倒れた場所にマグネットが残ること、**その勢力の
  ぶんだけ**動くこと、そして**変身では動かさないこと**。
- 3件目は**壊して確かめた**。死と変身を見分ける行を外すとこのテストが落ちる
  ことを確認している。控えの位置と変身した場所を別の座標にしてあるのは
  そのためで、同じにすると二重に動かしても気付けない。
