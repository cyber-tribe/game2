# 0055 map-expansion

## 背景

POPULOUS 2との比較調査で、S評価の1項目として「マップ拡張」が挙げ
られていた。現状の20×20は、道・城壁・津波防御・竜巻・渦巻きといった
「広い世界だから意味を持つ」要素が成立しにくいほど狭い。一方で調査
自身が「64×64化した場合、`gatherSystem`/`walkerCombatSystem`の
O(n²)処理が再現される可能性がある」と釘を刺しており、無計画な拡張は
性能問題を招くリスクが高い。本PRは、既存のレンダリング・シミュレー
ション実装のまま安全に拡張できる幅を実測した上で、その範囲内で
拡張する。

## 依存関係

本PRは`match-length-tuning`ブランチ（PR #58）の上に作成している
——`houseGrowth.ts`/`settle.ts`の詰み回避修正が先に入っていないと、
マップが広がって`maxHousesPerFaction`が増えるほど「両陣営とも上限・
ウォーカー0体」という稀な詰み状態に陥る余地も増えてしまうため。
PR #58が先にマージされる必要がある。

## 測定1：レンダリング負荷（ブラウザ実測）

`IsoRenderer.redraw()`は`app.ticker`から**無条件に毎フレーム**呼ばれ、
マップ全体の頂点を毎回走査する（溶岩の明滅アニメーションなどが常に
動いているため、地形編集時だけ再描画する設計にはなっていない）。
つまりこの関数のコストはタイル数にほぼ比例して常時かかり続ける
——ここがマップ拡張で最初に壊れる可能性が高い箇所だと判断した。

ヘッドレスChromiumで`renderer.redraw`を計装し、実際に3秒間（約100〜
150フレーム）の呼び出し時間を計測：

| マップサイズ | タイル数(倍率) | 平均 | p95 | 最大 |
|---|---|---|---|---|
| 20×20（現状） | 400 (1x) | 0.83ms | 1.5ms | 5.2ms |
| 28×28 | 784 (2.0x) | 1.24ms | 2.2ms | 2.9ms |
| **32×32（採用）** | **1024 (2.56x)** | **1.83ms** | **2.5ms** | **9.3ms** |
| 36×36 | 1296 (3.24x) | 2.56ms | 4.8ms | 11.5ms |
| 40×40 | 1600 (4.0x) | 4.60ms | 14.7ms | 18.5ms |

60fpsのフレーム予算（約16.6ms）に対し、40×40では一部のフレームが
ほぼ予算を使い切ってしまう（体感できるカクつきが起きるレベル）。
32×32ならp95が2.5ms（予算の15%程度）に収まり、実機（今回の計測
環境より非力な可能性がある低価格スマートフォン）でも十分な余裕が
残ると判断し、これを採用した。

**残作業**として明記する通り、これ以上の拡張（調査資料が示唆した
64×64など）には、`redraw()`を「毎フレーム全再描画」から「地形形状は
編集時のみ再描画し、溶岩の明滅など動くものだけ毎フレーム重ねる」
方式へ分離するような、レンダリング側の最適化が別途必要になる。

## 測定2：maxHousesPerFactionのスケール抑制

`TILES_PER_HOUSE_CAP`（土地不足の代用値）を据え置くと、タイル数が
2.56倍になった分だけ`maxHousesPerFaction`もそのまま2.56倍
（50→128）になり、`walkerCombatSystem`/`gatherSystem`のO(n²)処理の
最悪ケースコストが最大で2.56²≈6.5倍に膨らむ恐れがある。

調査資料自身も指摘する通り、広いマップの価値は「兵力を単純に増やす
こと」ではなく「前線・後方・距離・地形の多様性」といった**空間的な
余地**にある。そこで`TILES_PER_HOUSE_CAP`を8→12に引き上げ、
`maxHousesPerFaction`の伸びを2.56倍ではなく約1.7倍（50→85）に
抑えた——マップの面積は大きく広がるが、上限人口の伸びは緩やかに
する形。

## 測定3：試合時間の再検証

`plan/0053-match-length-tuning.md`と同じ手法（Simulationを直接
バンドルしAI放置シナリオで測定）で、32×32・`TILES_PER_HOUSE_CAP=12`・
`MIN_ARMAGEDDON_TIME=600`（既存のまま）での試合時間を40戦測定した。

- 40戦すべてが30分以内に終了（詰みゼロ）。
- 平均約728秒（約12.1分）、中央値約723秒（約12.05分）、
  最短約668秒（約11.1分）、最長約958秒（約16.0分）。

20×20時点（平均約677秒/約11.3分）よりわずかに伸びている
（陣営間の移動距離が伸びたため、と考えられる）が、目標の10〜15分
の範囲にほぼ収まっており、`MIN_ARMAGEDDON_TIME`の追加調整は不要と
判断した。

## 変更内容

- `main.ts`：`WORLD_WIDTH`/`WORLD_HEIGHT`を20→32。
- `game/constants.ts`：`TILES_PER_HOUSE_CAP`を8→12。

カメラの自動フィット（`baseScale`を`renderer.mapPixelHeight`から
毎回算出）・ミニマップ・集結シンボルの初期配置（`worldWidth`/
`worldHeight`に対する相対座標）は、いずれも既にマップサイズに依存
しない形で実装されていたため、この2つの定数変更以外のコード変更は
不要だった。

## テスト

- `src/game/simulation.test.ts`：`TILES_PER_HOUSE_CAP`変更に合わせ、
  上限到達を検証するテストのワールドサイズを4×4→5×5へ調整
  （25÷12=2.08→上限2、という計算が成り立つように）。
- `npm run typecheck` / `npm run test -- --run`（256件）/
  `npm run build`がすべて成功。
- ヘッドレスブラウザで32×32のデフォルトカメラ・ズームアウト時の
  見た目を確認——自動フィット・ミニマップとも問題なく表示された。
- 上記の測定1〜3（レンダリング負荷・試合時間）を参照。

## 残作業

- さらなる拡張（調査資料が触れた64×64など）には、`IsoRenderer.
  redraw()`を「毎フレーム全再描画」から脱却させるレンダリング最適化
  が前提になる。今回はその最適化に踏み込まず、既存実装のまま安全な
  範囲に収めた。
- `plan/0054-terraform-brush.md`（長押しブラシ造成）は本PRとは別
  ブランチだが、広いマップほど効果が大きい変更のため、両方が
  マージされた状態で改めて操作感を確認するとよい。
- 土地不足の本実装（地形ベースの本物の建築可能面積判定）が入れば、
  `TILES_PER_HOUSE_CAP`という代用値自体が不要になる。
