# 0053 match-length-tuning

## 背景

POPULOUS 2との比較調査で、S評価の1項目として「ゲームテンポを通常
10〜15分程度まで検証」が挙げられていた。これまでの一連のペーシング
調整（plan/0043〜0046：地形の荒さ、騎士のクールダウン、最終決戦発動
タイミング、最終決戦の行軍速度）で、AI同士（プレイヤーは何も操作せず
放置する「AI放置シナリオ」）での平均試合時間は約109秒→約303秒まで
延びていた。これを実際に測定し直し、10〜15分（600〜900秒）に近づける
のが今回の作業。

## 測定方法

`Simulation`クラス単体（レンダリング無し）をNode上でesbuildにより
バンドルし、`createHeightmap(20, 20, "grass")`で作成した`heightmap`を
渡して`new Simulation({...})`を生成、`sim.update(0.1)`を
`sim.getOutcome().over`になるまで回し続けて経過時間を記録する、という
スクリプトを一時的に作成して実行した（リポジトリには残していない）。
プレイヤー側は一切操作しない「AI放置シナリオ」——既存のペーシング
調整と同じ測定方法。

## 発見1：MIN_ARMAGEDDON_TIMEはもう律速していない

現状（180秒）で20戦測定したところ、平均約251秒、最短207秒、最長296秒
——180秒という下限にほとんど張り付いていない。つまり
`ARMAGEDDON_POPULATION_RATIO`（人口比1.8倍）に実際に到達する時刻の方が
既に180秒より遅く、下限はもう律速要因ではなくなっていた。

## 発見2：MIN_ARMAGEDDON_TIMEを上げると"詰み"が起きることがある

`MIN_ARMAGEDDON_TIME`を480秒→600秒と上げて再測定したところ、
600秒の設定で30戦中2戦が60分のタイムアウトまで終了しなかった
（約6.7%）。詳細をログすると、両陣営とも
`houses === housesCap`（上限）かつ`walkers === 0`という状態で完全に
固まっていた。

原因は2つの既存の抜け穴の組み合わせ：

1. `houseGrowth.ts`の上限チェック（`houseCountByFaction < maxHousesPerFaction`
   の間だけウォーカーを輩出）は、**その家が上限到達より前に定住して
   できた家**までは防げない。`settle.ts`（定住システム）自体は
   `maxHousesPerFaction`を一切見ておらず、既に上限へ向かっていた
   ウォーカーはそのまま定住できてしまうため、家の数が長時間かけて
   静かに上限を超えることがある。
2. 一度両陣営とも「家は上限（またはそれ以上）、ウォーカーは0体」
   という状態に落ち込むと、二度と抜け出せない——`houseGrowth`の
   人口オーバーフローも`settle`の新規定住も、どちらも家の数の上限
   チェックで塞がれているため、新しいウォーカーが二度と生まれない。
   ウォーカーがいなければ戦闘も家の奪取も起きず、人口比が
   `ARMAGEDDON_POPULATION_RATIO`を跨ぐこともない——`docs/game-system.md`
   が明言する「引き分けはなく」に反して、試合が永久に終わらなくなる。

`MIN_ARMAGEDDON_TIME`を延ばすこと自体がこの引き分けを作ったわけでは
ない（理論上は旧来の180秒設定でも起こり得た）が、試合時間を延ばす
ほど、この稀な均衡状態に両陣営が同時に落ち込むまでの猶予（＝発生確率）
が増える。今回この抜け穴を塞ぐこと自体が、10〜15分化の前提条件になった。

## 修正

### settle.tsにmaxHousesPerFactionを追加

`SettleConfig`に`maxHousesPerFaction`を追加し、`houseGrowth.ts`と
全く同じロジック（フェーションごとの現在の家数を数え、上限以上なら
その回の定住をスキップ）でガードする。上限に達したフェーションの
ウォーカーは家を建てられず、`MoveTarget`を持たないまま
`createWanderTargetSystem`に次のtickで新しい目的地を渡され、
彷徨い続ける——消えて家になるのでも詰まるのでもなく、「行き場のない
余剰人口」として引き続き戦闘・集結の戦力になる。

### houseGrowth.tsに「詰み回避弁」を追加

上記だけでは、家の数の上限超過を防げても、「両陣営とも上限ぴったり・
ウォーカー0体」という状態そのものは（超過なしでも）到達可能で、
根本原因は解消されない。そこで`createHouseGrowthSystem`の上限判定に
例外を追加：**そのフェーションが現在ウォーカーを1体も持たない場合は、
上限を無視して1体だけ輩出を許可する**。

ウォーカー0体の状態は「全滅寸前」または「人口を家に使い切った」状態
であり、この1体が生まれることで：
- 彷徨う・集結する・戦うことができる（`settle`は依然として上限で
  ガードされているため、この1体はすぐには新しい家にはならない）。
- 両陣営が同時にこの状態へ落ち込んでも、それぞれ1体ずつ脱出用の
  ウォーカーを得るため、二体がいずれ接触すれば戦闘で決着がつき、
  人口比の膠着も崩れる。

同じ家のpopulationが1tickで複数回オーバーフローしても、この抜け道は
「ウォーカー0体→1体になった時点」で閉じる（2体目以降は通常の上限
チェックに戻る）ため、無制限に上限を無効化するものではない。

## 発見3：MIN_ARMAGEDDON_TIMEの再調整

上記の修正後、`MIN_ARMAGEDDON_TIME = 600`（10分）で80戦再測定した
ところ、**80戦すべてが30分以内に終了し（詰みゼロ）**、平均約677秒
（約11.3分）、中央値約673秒（約11.2分）——目標の10〜15分にきれいに
収まった。

## テスト

- `src/game/systems/settle.test.ts`：上限到達済みフェーションの
  ウォーカーが定住できないこと、別フェーションが上限でも自分が
  上限未満なら定住できること、`maxHousesPerFaction`省略時は無制限
  であることを検証。
- `src/game/systems/houseGrowth.test.ts`：ウォーカー0体のフェーションは
  上限を無視して1体だけ輩出されること（詰み回避弁）、既にウォーカーが
  1体でもいれば通常通り上限で止まること、1tickで複数回オーバーフロー
  しても回避弁は1回しか使われないことを検証。既存の「上限で完全に
  停止する」テスト2件は、いずれもウォーカー0体から始まっていたため
  回避弁が意図せず作用してしまう構成だったので、あらかじめウォーカー
  を1体存在させる形に修正した（回避弁が要らないシナリオへ変更）。
- `src/game/simulation.test.ts`：両陣営とも上限・ウォーカー0体という
  詰み状態から、実際に双方がウォーカーを再び持てるようになることを
  統合テストとして検証（衝突の偶然に左右されないよう、2陣営の家を
  マップの離れた位置に配置）。既存の「上限で止まる」統合テストは、
  両陣営の家を同じ座標に置いていたため回避弁のウォーカー同士が
  衝突して相討ちになる可能性があり非決定的になった——ウォーカー数の
  厳密な検証はやめ、家の上限自体は保たれることのみを検証する形に
  変更した。
- `npm run typecheck` / `npm run test -- --run`（256件、5回連続実行
  してすべて成功）/ `npm run build`がすべて成功。
- 上記のNode直接実行スクリプトによる測定（80戦、30分タイムアウト）で
  詰みゼロ、平均約11.3分を確認。

## 残作業

- 今回はAI放置シナリオ（プレイヤー操作なし）でのみ測定した。実際の
  プレイヤーは奇跡や地形操作で試合を早めたり長引かせたりできるため、
  体感時間はこれと異なりうる。
- マップサイズ拡張・造成UIの省力化（S評価の残り2項目）は本PRの
  スコープ外。マップを広げれば`maxHousesPerFaction`や移動時間も
  変わるため、それらが入った際は本PRの数値を再測定する必要がある。
- 詰み回避弁は「稀な膠着を壊す」ための最小限の対処であり、根本的な
  土地不足モデル（`docs/game-system.md`が触れている、まだ未実装の
  本物の土地不足）が入れば、この種の抜け道自体を作り直す必要が
  出てくる可能性がある。
