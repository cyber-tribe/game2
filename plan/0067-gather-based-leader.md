# 0067: リーダーを「集結」の結果として誕生させる

## 背景

ユーザーから、指定Wiki（Populous 2）本文と現行game2実装を突き合わせた詳細な
再照合レポートが届いた。多くのS級差分（64×64化、造成ブラシ、固有SE、
ワールドごとの造成制限、農地、照会、人口比較など）は既に埋まっている一方、
新たに次の2点が「ゲームの根幹に関わる未発見差分」として最優先で指摘された。

1. **リーダー誕生条件**: Wikiでは「集結」を選んだ状態でシンボル（集結地）へ
   最初に到着した信者がリーダーになり、他の信者がそのリーダーへ集まって
   大きな集団を作り、ヒーロー化する。これが「軍隊を作る準備そのもの」という
   ゲームプレイになっている。一方、既存の`leaderSystem`は「リーダーが
   いなければ、生存Walkerを無条件に昇格させる」という実装で、行動方針
   （behaviorMode）と無関係にリーダーが常時存在してしまっていた。
2. **啓示の排他性**（今回は着手せず、次点として記録）: 「合体」「戦闘」は
   対象がいなければ「定住」にフォールバックする、という設計。調査の結果、
   `createWanderTargetSystem`/`createSettleSystem`が元々モード非依存で
   動いているため、実は現状でも同様のフォールバックは部分的に発生している
   ことが判明した（`docs/game-system.md`の「戦闘してから定住」という複合
   指示の記述とも整合）。ここは今回は変更せず、次の優先度として残す。

今回のPRはユーザーが最優先に挙げた①「リーダー生成を『集結』のゲームプレイに
戻す」を実装する。

## 設計

### リーダーは「集結」モードでのみ生まれる

- `leaderSystem`（`src/game/systems/leader.ts`）: 「リーダー不在なら生存
  Walkerを無条件昇格」から、「`behaviorMode === "gather"`のときに限り、
  集結地（`shrinePosition`）から`GATHER_RANGE`以内にいる、その陣営の
  Walkerのうち最も近いものを昇格」に変更。原作の「最初にシンボルへ
  到着した者」を、実際にシンボルへ到達した歩行者だけを対象にすることで
  近似した。
- 新規`gatherTargetingSystem`（`src/game/systems/gatherTargeting.ts`）:
  「集結」モードの陣営について、リーダーがまだいなければ全員を集結地へ、
  リーダーがいれば全員（リーダー自身を含む）をリーダーの現在地へ向かわせる。
  既存の`goToShrineSystem`と同じ「目標を持たない歩行者にだけ割り当てる」
  パターンを踏襲し、`createWanderTargetSystem`に先を越されないようにした。
- 既存の`gatherSystem`（合体・吸収）はそのまま。歩行者が実際に近づいて
  くるようになったことで、偶然の接触任せだった合体が機能するようになった。

### 副作用: リーダーが「集結」中に即座に家になってしまう問題

`gatherTargetingSystem`はリーダー自身にも「自分の現在地」を目標として
割り当てる（`createWanderTargetSystem`に横取りされないようにするための
実質ノーオペレーション）。しかしこれは距離0の目標であり、`movementSystem`は
即座に目標をクリアするため、同じtickの後段にある`createSettleSystem`が
「目標なし＝到着」と誤認し、昇格した直後のリーダーをその場で家に変えて
しまっていた（ヘッドレスPlaywrightでの実機検証で発見）。

`createSettleSystem`に、「集結」モード中の陣営のリーダーを対象から除外する
処理を追加して解決した。`goToShrine`モードでは従来通りリーダーが集結地に
到着したら定住する（新拠点の建設として意図された挙動、既存テストの
「walks a lone leader to a relocated shrine and settles it there」が
明示）ため、除外は「集結」モード限定とした。

### 敵AIも「集結」を使うようにする

敵の`knightify`（`enemyMiracles.ts`の自動騎士化）はリーダーの存在が前提
条件だが、敵AIはこれまで「settle」と「fight」の二択しか使っていなかった
ため、上記の変更のままだと敵は永久にリーダーを持てず、騎士化能力が
機能しなくなってしまう。`enemyAi.ts`に「リーダーがまだいなければ
（fightするほど攻撃的でも脅威下でもない限り）gatherする」という分岐を
追加し、敵も自陣営のルールでリーダーを獲得できるようにした
（`enemyTerraform.ts`の「敵の神はプレイヤーと同じルールで介入する」と
同じ思想）。

### 最終決戦（armageddon）がリーダー不在でも機能するように

`triggerArmageddon`は「集結シンボルへ」の進軍を`goToShrineSystem`（要:
生存リーダー）に委ねているが、そのマッチが一度も「集結」を使っていなければ
`leaderId`が未設定のままの可能性が生まれた。最終決戦は後戻りのない一方的な
イベントであり、誰がその場しのぎの先導役になるかはゲーム的に重要でないため、
`triggerArmageddon`自身がリーダー未設定の陣営に対して生存する任意の
Walkerを強制的にリーダーとして割り当てるようにした（既存の無条件
`leaderSystem`が行っていたのと同じロジックを、このタイミングだけ復活
させた形）。

## 検証

- `npm run typecheck` / `npm run test -- --run`（357件、複数回連続実行で
  再現確認）/ `npm run build` すべて通過。
- `leader.test.ts`を全面的に書き直し（集結地に到着した歩行者のみ昇格、
  集結モード以外では昇格しない、最も近い候補が選ばれる、他陣営は対象外、
  既存リーダーは維持、リーダー死亡時の後任昇格、歩行者不在時は何もしない）。
- 新規`gatherTargeting.test.ts`（リーダー不在時は集結地へ、リーダー自身も
  自分の位置へ再ターゲットされて放浪しない、フォロワーはリーダーへ、
  敵陣営のリーダーへは向かわない、モード外では何もしない、既存の目標は
  上書きしない、seeking以外は無視、リーダーが無効なら集結地へフォール
  バック）。
- `enemyAi.test.ts`を更新（リーダー不在時はgather、既にリーダーがいれば
  settle）。
- `armageddon.test.ts`にリーダー強制割り当てのテストを追加（未設定の陣営に
  割り当てる／既存の生存リーダーは維持する）。
- `simulation.test.ts`の関連する結合テスト（デフォルトsettleではリーダー
  なし、gather選択で即座にリーダーが付く、goToShrineでの進軍と定住、
  騎士化、最終決戦の決着）を新しい挙動に合わせて書き直した。armageddonの
  結合テストは、ヒートマップなしだと`createWanderTargetSystem`の徘徊が
  無制限に広がり稀に規定tick内に決着しないことが判明したため、他の
  ヒートマップ付きテストと同様にフラットなヒートマップを渡すようにして
  安定させた（本PRの変更が原因で新たに発生したものではなく、既存の
  潜在的な不安定要因が偶然表面化したもの）。
- headless Playwrightで実機シナリオを検証: デフォルトのsettleモードでは
  数秒待ってもリーダーが付かないこと、「集結」に切り替えると（歩行者が
  集結地付近にいる限り）ほぼ即座にリーダーが付くこと、経済を回してから
  集結→騎士化まで一連の流れが機能することを、`simulation.knightify`の
  直接呼び出しで確認した（UIのトースト/ツールボタン経由のクリックは
  テストスクリプト側のタイミング起因で不安定だったため、ゲームロジック
  自体の検証はAPI直叩きで行った）。
