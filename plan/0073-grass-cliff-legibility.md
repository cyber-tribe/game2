# 芝生と断面（崖）の視認性改善

## 背景

ユーザーから「芝生とその断面の表現がいけてない、視認性が悪い」との
指摘。続けて「前に見せた原作のデザインも確認して、ライティングと影の
問題もありそうですね」との追加フィードバックがあり、セッションに
アップロード済みの原作（Populous系タイトル）のスクリーンショットを
改めて確認した上で対応した。

## 診断

`src/render/IsoRenderer.ts`を調査し、2つの独立した問題を特定:

1. **芝生のディザーパターンが荒く見える**: `createDitherTexture`が
   8x8ピクセルのタイル状ディザーテクスチャを作る際、各ピクセルの
   色決定に`tileHash(x, y) = frac(sin(x*127.1+y*311.7)*43758.5453)`
   （ボルケーノのひび割れ角度用に作られた既存のハッシュ関数）を
   流用していた。このハッシュは連続的な広い範囲の入力に対しては
   良いばらつきを示すが、8x8のごく小さい整数格子でサンプリングすると
   周期的なエイリアシングを起こし、ランダムな斑点ではなく数個の
   大きな三角形ブロックが繰り返されるパターンになっていた
   （実機スクリーンショットで確認済み）。
2. **崖の断面がほぼ見えない**: `drawCliffWalls`は崖の壁を
   「上面の色を35%黒に近づけただけ」の単色で塗っていた。芝生の
   場合、上面の基準色`TERRAIN_COLOR.grass`（0x4a8c3f）を35%暗くすると
   (48, 91, 41)になるが、これは芝生ディザーの暗い斑点色
   `GRASS_SPECKLE_COLOR`（0x336228 = (51, 98, 40)）とほぼ同一色。
   つまり暗い斑点の真下に崖があると、色差がほぼゼロで境界が
   全く見えなかった。これが「視認性が悪い」の直接的な原因。

さらに、原作のスクリーンショットを詳細に確認したところ
（`/root/.claude/uploads/`内の該当画像を参照）、同じ台地の2つの
可視な崖面が明確に異なる明るさで塗られている——一方はオレンジ寄りの
明るい茶色、もう一方（プレイヤーに近い前面）はより暗いマルーン系の
茶色。これは固定された光源方向に基づくディレクショナルシェーディング
であり、このレンダラーには一切実装されていなかった
（4方向の壁が常に同じ1色）。これがユーザーの言う
「ライティングと影の問題」。

## 対応

`src/render/IsoRenderer.ts`:

1. **ディザーハッシュの差し替え**: `createDitherTexture`専用の
   `ditherPixelHash`を新設（整数の乗算+xorシフトによる
   "hash32shift"系のビット混合ハッシュ）。小さな整数格子でも
   周期性を持たず、細かい斑点として見えるようになった。
   `tileHash`自体はボルケーノのひび割れ用途では問題ないため
   変更していない。
2. **芝生の崖に専用の土色を導入**: `GRASS_CLIFF_COLOR`
   （0x8a6a45、アーシーな茶色）を新設。芝生地形の崖だけは
   この色を基準に暗くし、それ以外の地形（砂漠・雪原・岩盤）は
   従来通り自身の上面色を暗くする。色相そのものを変えることで、
   芝生ディザーのどのピクセルの真下でも確実にコントラストが
   出るようにした。原作や多くの地形ベース建設ゲームが
   「上は緑、断面は土色」という配色をしているのに倣った。
3. **崖壁のディレクショナルシェーディング**: `drawCliffWalls`が
   4方向すべてに同じ`CLIFF_SHADE_AMOUNT`（35%減光）を使っていたのを
   やめ、光源を北東方向（`toScreen`の -y/+x 方向）に固定した
   2階調シェーディングに変更。北・東向きの壁は光源側を向くため
   明るい`CLIFF_LIT_SHADE_AMOUNT`（15%減光）、南・西向きの壁は
   `CLIFF_SHADE_AMOUNT`（35%減光、従来通り）とした。原作の
   スクリーンショットで確認した「同じ台地の2つの壁面が異なる
   明るさ」を再現している。

## 検証

- `npm run typecheck`: エラーなし
- `npm run test -- --run`: 410件全て成功。
  `IsoRenderer.test.ts`に以下を追加/更新:
  - 崖壁が上面より暗いことを検証する既存テストを、方向によって
    2階調になったことを反映して更新（3色 = 上面 + 明/暗の壁2色）。
  - 芝生の崖が緑ではなく土色（赤≧緑>青のチャンネル関係）で
    塗られることを検証するテストを更新（2階調分）。
  - 台地の北・東の壁が南・西の壁より明るいことを、
    `drawCliffWalls`の`.poly([topA.sx, topA.sy, ...])`の
    最初の頂点座標から幾何学的に各壁の方向を特定して検証する
    新規テストを追加。
- `npm run build`: 成功。
- Playwright（chromium）による実機確認: 最初の（草原）ワールドで
  地形をなぞって隆起させ、ズームインしたスクリーンショットを撮影。
  以前は完全にのっぺりした一色に見えていた地形の起伏が、
  ディザー修正だけで既にはっきり見えるようになり、さらに
  ディレクショナルシェーディングにより同じ台地の隣接する2つの
  崖面が異なる明るさで塗り分けられ、原作の見た目に近い立体感が
  得られたことを確認した。

## 追記: 「全ての面が断層になる」問題への対応

上記の対応後、ユーザーから再度フィードバック:「原作と比較してください。
全ての面が断層(茶色)になるのは違和感です」。

### 診断

何も編集していない生成直後のワールドをスクリーンショットで確認したところ、
マップのほぼ全域が茶色の崖で埋め尽くされていた。原因は崖の可視性を
直したことそのものではなく、`src/world/heightmap.ts`の`createHeightmap`が
`plan/0043-terrain-roughness.md`で**意図的に**導入した高周波ノイズ
（隣接頂点の18%が3段以上の差を持つ）。崖が見えなかった以前はこの粗さが
隠れていたが、可視化した今、地形本来の粗さがそのまま「壁だらけ」に
見えてしまっていた。

`plan/0043`は「城レベルの平坦さがタダで手に入る」問題を防ぐための
意図的な選択であり、単純に地形を滑らかに戻すと同じ問題が再発する。
そこでユーザーに3つの対応方針（地形生成を滑らかにする／小さな段差だけ
滑らかにする／崖の色をもっと控えめにする）を提示したところ、
「すべて取り組んでください。まずは原作と同等になることを目指しましょう」
との回答を得た。

### 対応（3方向すべて）

1. **地形生成の振幅を控えめに**（`heightmap.ts`）: 周波数（1.3/1.1/0.9）は
   `plan/0043`の意図（平坦さをタダで与えない）を保つためそのままに、
   振幅を1.5/1.5/2→1.2/1.2/1.6に縮小。隣接頂点の3段以上の差が18%→7%未満に
   減少しつつ、20x20マップでcastle対応0%を維持（manorは2.5%→約6%と
   小幅な上昇に留まる——`heightmap.test.ts`の既存回帰テストで検証）。
2. **崖の減光量を落差に比例させる**（`IsoRenderer.ts`）:
   `CLIFF_SHADE_AMOUNT`/`CLIFF_LIT_SHADE_AMOUNT`を「常に全力で暗く
   する」から「`CLIFF_FULL_SHADE_DROP`段分の落差で頭打ちになり、
   それ未満は落差に比例して減光する」方式に変更。地形生成のありふれた
   1〜2段の起伏は控えめな陰影に、火山・地震・複数回の地形操作などによる
   本物の段差は従来通り力強く表現される。
3. **描画時の高さの量子化（新規）**: `VISUAL_ELEVATION_BUCKET`（2段）を
   導入し、`redraw()`内の`tileElevation`が返す高さを2の倍数に丸めるよう
   にした。地形データそのもの（`countFlatNeighbors`が読む生の頂点値）は
   一切変更せず、**描画だけ**が粗いノイズの大半を同じ平坦な台地へ吸収
   する。上記2点だけでは「壁の色」は薄まっても「壁の数」自体は変わらず
   視覚的な改善が乏しかったため、実際に効いたのはこの量子化だった——
   隣接タイルの多くが同じ丸め後の高さに揃うことで、本当に平坦な広い
   緑地が生まれ、崖は「稀に起きる本物の段差」として際立つようになった。

### 検証

- `npm run typecheck` / `npm run test -- --run`（412件）/ `npm run build`:
  すべて成功。
- `heightmap.test.ts`の「城レベルの平坦さをタダで渡さない」回帰テストは
  無修正のまま通過（振幅縮小後もcastle対応0%を維持）。
- `IsoRenderer.test.ts`に追加:
  - 小さな落差（2段）が本物の崖（capを超える落差）よりずっと控えめに
    減光されることを検証するテスト。
  - `VISUAL_ELEVATION_BUCKET`により、ごく小さな高さの違い（隣接頂点の
    ±1程度）が同じ丸め後の高さに吸収されて壁が一切現れないこと、かつ
    バケットを跨ぐ本物の差では引き続き壁が現れることを検証するテスト。
  - 既存の方向別シェーディングのテスト群は、複数タイルにまたがる
    シーンだと`toScreen`の投影が異なる(x, y, elevation)の組を同じ
    画面座標へ収束させてしまい、頂点座標による壁の特定が信頼できない
    ことが判明したため、1タイルだけの最小構成（4辺すべてがマップ外
    既定値0に接する）に単純化し、描画順（north/east/south/west）で
    直接読み分ける方式に書き換えた。
- Playwright（chromium）で編集前の生成直後ワールドを撮影し、施策前後を
  比較: 施策前はマップのほぼ全域が茶色の崖で埋まっていたが、施策後は
  広い緑の平地に時折はっきりした崖が現れる、原作に近い見た目になった
  ことを確認した。地形を実際に隆起させた際も、方向別シェーディングを
  伴う明瞭な崖が正しく表示され、コンソールエラーも無かった。

## 追記2: 「段差は坂であって断層ではない」への対応（描画モデルの作り直し）

上記の量子化対応の後、ユーザーから原作の別のスクリーンショット
（草原の台地に木・水・家が配置されたダイオラマ風の画像）とともに
再度指摘: 「そもそも2段3段の段差があっても坂になるだけで、断層には
なりません」。

### 診断

この指摘は「壁の色や減光量のチューニングが足りない」という話ではなく、
「ブロック単位で平均高さに丸め、隣接タイルとの差を垂直な壁として描く」
という`plan/0064-terraced-terrain.md`以来のレンダリングモデル自体が
原作と根本的に違う、という指摘だった。新しい参考画像を精査すると、
同じ台地の起伏はすべて緑の濃淡が付いた三角形ファセット（傾斜面）として
連続的に表現されており、垂直な断面（茶色）が現れるのは水際とマップ
外周のジオラマ的な縁取りだけだった。

アーキテクチャの方向転換についてユーザーに確認したところ
（「地形描画を『ブロック+垂直な崖壁』から『頂点の高さをそのまま使った
傾斜面+陰影』へ作り直す、という理解で進めてよいですか？」）、
「はい、その方向で進めてください（推奨）」との回答を得た。

### 対応

`src/render/IsoRenderer.ts`のレンダリングモデルを全面的に作り直した:

1. **タイルごとの平均高さブロック→頂点ごとの三角形メッシュへ**:
   各タイルは自身の4頂点の実際の高さを使い、(x,y)-(x+1,y+1)の対角線で
   2枚の三角形に分割して描く（`fillTerrainTriangle`）。3頂点は必ず
   同一平面になるため、4頂点そのままの四角形（歪んで非平面になり得る
   「鞍点」形状）と違い、法線が一意に定まる。
2. **法線ベースのディレクショナルシェーディング**: 固定光源方向
   `LIGHT_DIRECTION`（北東寄り、真上寄り）に対する各三角形の法線の
   内積から明るさを計算する`triangleBrightness`/`faceBrightness`を
   新設。平らな地面はちょうど基準色のまま、光に向いた面はわずかに
   明るく、逸れた面は暗くなる——量子化やバケット、しきい値は一切なし。
   ごくわずかな段差もそのまま「ごくわずかに傾いた面」として滑らかに
   表現され、急な段差ほど自然に大きく傾き・大きく陰影が付く。
3. **垂直な壁はマップの本当の外周だけに限定**（`drawEdgeWall`）:
   従来の`drawCliffWalls`（タイル間の高さ差ならどこでも壁を描いていた）
   を廃止し、マップの真の境界（`x===0`/`x===width-1`/`y===0`/
   `y===height-1`）でのみ、海面まで垂直に落ちる壁を描く。原作の
   ジオラマ的な「台座の縁」表現に対応する、地形本来の意味ではなく
   マップの物理的な縁を表す特別な存在という位置づけ。
4. これに伴い、`VISUAL_ELEVATION_BUCKET`・`bucketElevation`・
   `CLIFF_SHADE_AMOUNT`・`CLIFF_LIT_SHADE_AMOUNT`・
   `CLIFF_FULL_SHADE_DROP`・`GRASS_CLIFF_COLOR`・`CLIFF_MIN_STEP`
   は全て削除。壁の「色」や「しきい値」をどれだけ調整しても、
   段差が壁として描かれること自体が原作と違う、という問題は解決
   できなかったため、これらのチューニング機構はもはや不要になった。
5. 芝生のディザー表現（`GRASS_FILL`）は、完全に平らな三角形にのみ
   適用する。傾いた芝生は他の地形と同じくプレーンな色合いでシェーディング
   する——ディザー柄と傾斜シェーディングを両立させる複雑さは今回の
   目的に見合わず、副次的に「地形を平らにする（建築の前提条件）」操作の
   視覚的な報酬にもなっている（手つかずの粗い傾斜地とは明確に見た目が
   変わる）。

`heightmap.ts`のデータモデル・生成ロジックは変更していない
（`createHeightmap`の粗さは追記1の振幅調整のまま）——今回の変更は
純粋にレンダリング層のみ。

### 検証

- `npm run typecheck` / `npm run test -- --run`（411件）/
  `npm run build`: すべて成功。
- `IsoRenderer.test.ts`の`describe("IsoRenderer.redraw (terraced blocks)")`
  ブロックを全面的に書き直し、新しい描画モデルに対応する
  `describe("IsoRenderer.redraw (sloped mesh)")`に置き換えた:
  - 海面と同じ高さのタイルは陰影の付かないフラットな四角形1枚のまま
    （水面表現は従来通り）。
  - マップ内部のタイル境界の高さ差は、どれだけ大きくても壁を一切
    描かず、常に2枚の傾斜三角形として——傾きが急なほど陰影も
    段階的に強くなることを検証（しきい値なし）。
  - 傾斜の向き（上りか下りか）によって陰影の濃淡が変わることを検証。
  - マップの真の外周だけは従来通り、方向別の濃淡を持つ垂直な壁が
    描かれることを検証。
  - 平らな芝生の三角形はディザーテクスチャで、傾いた芝生の三角形は
    プレーンな色合いで塗られることを検証。
- Playwright（chromium）で実機確認: 生成直後のワールド、および
  実際に地形を隆起させた後の両方をズームインしたスクリーンショットで
  撮影。原作の参考画像と同様、台地の起伏が滑らかな三角形ファセットの
  濃淡として連続的に表現され、内部に垂直な茶色い断面は一切現れず、
  マップの外周だけが黒い背景へ落ち込む壁として残っていることを確認。
  コンソールエラーも無かった。
