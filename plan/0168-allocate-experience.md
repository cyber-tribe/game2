# 0168 allocate-experience

## 経験点はプレイヤーが配分する

`plan/0161` は「使った系統に自動で入る」と実装した。根拠は
`docs/original-miracles.md` の「各カテゴリーのレベルを**上げていくことが
できる**」という一行で、そこから game2 が「使った系統が伸びる」と読んだ。

原文に当たると、**プレイヤーが振り分ける**と書いてあった。

> この辺りから、地上編終盤に向けて経験点を**地と気レベルに重点配分**して
> 下さい。（No.22-24）

> **経験点の使い道**に迷ったら水レベルを上げると、次の太陽神の宮で
> 役に立ちます。（No.31-33）

「重点配分」「使い道に迷ったら」——どちらもプレイヤーが選ぶ語である。しかも
2つ目は**次の面が何の神かを見て決めろ**と言っている。**どこへ入れるかを
選ぶこと自体が原作の遊び**であり、自動配分はそれを丸ごと落としていた。

（`plan/0167` と合わせて、`docs/original-miracles.md` の要約を資料そのものと
思い込んで実装した4件目である。）

## 何点配れるのか

**稲妻マークの数**である。

> 序盤さえ乗り切れば、**経験点10点**を取ってクリアできるでしょう。（No.37-39）

面の評価の上限が「稲妻マーク10個」なので、**マークがそのまま点**だと読める。
1面で最大10点。

## どこで配るか

**面をクリアした画面**——「戦いの記録」の中、パスワードの直前に置いた。

パスワードは既に経験点を運んでいる（`plan/0161`）ので、配分の結果がその場で
パスワードに反映される。**決めてから書き写す**ことになり、順番として正しい。
次の面の神が何系統かは世界選択に出ているので、「次の太陽神の宮で役に立つ」
という原作の考え方もそのまま成立する。

各系統の行に「次の1段まで残り何点か」を出した。どこへ入れるか決める材料は
これである。

## レベルの段差を10に下げた

`MIRACLE_LEVEL_STEP` は 20 だった。自動配分では1面のマークが**使った系統
すべてに**入っていたので、同じ点が何倍にもなって届いていた。配分制では1面
につき合計10点までなので、そのままでは段が上がらない。

10 なら、1系統に寄せて4面ぶんで最大（Lv5）に届く。48面あるので複数系統を
育てられ、それでいて「重点配分」が形式ではなく選択として効く。

## 検証

- `npm run typecheck` / `npm run build` パス、テスト1014件パス（+3）。
- `miracleLevels.test.ts` 7件——指定した系統に入ること、加算されること、
  まとめて入れられること、渡された経験点を書き換えないこと、負にならない
  こと、`MIRACLE_LEVEL_STEP` 点で段が上がること、1面ぶん（10点）を1系統に
  寄せてもいきなり最大にはならないこと。
- 実機（ヘッドレス Chromium、実ビルドを `/game2/` で配信、seed 固定）で
  勝利画面まで通した。パネルは**勝ったときだけ**出る（負けと引き分けでは
  出ない）ので、最終決戦で決着させて確認している。各系統5点から始めた回：

  ```
  TITLE:  GAME OVER — player wins
  RATING: 評価 ⚡⚡・・・・・・・・
  見出し: 経験点 2 点 —— 上げたい系統に振り分けてください
  パネル: 人 Lv1 次まで 5 ＋ | 植物 Lv1 次まで 5 ＋ | …（6系統）
  配分前: athens-2.050505050505
  気に1点: athens-2.050505060505
  人に1点: athens-2.060505060505
  ```

  桁の位置が `MIRACLE_SCHOOLS` の順（人・植物・地・気・火・水）と一致し、
  「次まで」も入れた2系統だけ 5→4 に動く。使い切ると＋が全て無効になる。
  経験点を上限（`zz`）まで持たせた回では、1点入れてもパスワードが変わら
  ない——`encodeExperience` が `MAX_ENCODED_EXPERIENCE` で頭打ちにする
  ためで、これも意図どおりである。
