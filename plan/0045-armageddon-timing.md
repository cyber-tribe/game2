# 0045 armageddon-timing

## 背景

`plan/0043`（地形の高周波化）・`plan/0044`（騎士の焼き討ちに休憩）
と続けて2分決着問題に取り組んできたが、`plan/0044`時点の実測でも
中央値はまだ2分弱だった。両方の残作業に共通して挙げていた、
「`enemyMiracles.ts`のArmageddon自動発動の人口比閾値（1.8倍）に
使う`totalPopulation`が、家の`population`（頻繁にウォーカーへ変換
されてリセットされる値）とウォーカー数の単純合算で振れ幅が大きく、
早期に閾値を超えやすい」という要因に着手する。

## アプローチ

`enemyMiracles.ts`の`createEnemyMiracleSystem`に、試合開始からの
経過秒数を数える`elapsed`カウンタを追加し、Armageddon分岐だけ
`elapsed >= minArmageddonTime`（デフォルト`MIN_ARMAGEDDON_TIME`＝
180秒、`src/game/constants.ts`に新設）を追加条件にした。

- 180秒はあくまで「下限」であり「目標試合時間」ではない：人口比が
  180秒経過前に閾値を超えていても、経過するまでは
  Armageddon分岐を素通りし、次善の一手（騎士化・火山・地震）に
  フォールスルーする——これは既存の「手が届かなければ次の安い
  手段へ」という設計をそのまま利用しているだけで、新しいフォール
  バック処理を追加してはいない。
- 180秒を過ぎて以降は、通常通り人口比が閾値を超えた瞬間に発動する
  （＝「180秒の間だけ待たせる」のであって「180秒後に必ず発動する」
  わけではない）。
- `EnemyMiracleConfig`に`minArmageddonTime`を追加し、
  `decisionInterval`などと同様にテストから上書きできるようにした。

## テスト

- `src/game/systems/enemyMiracles.test.ts`：
  - `minArmageddonTime`未満の経過時間では、どれほど人口比が
    決定的でもArmageddonが発動しないこと。
  - `minArmageddonTime`を超えた回では発動すること（1回目は
    フォールスルーでマナを使い切るため、2回目呼び出し前に
    マナを補充している——収入のタイミングではなく経過時間ゲート
    そのものを検証するためのテスト上の単純化）。
  - 既存の「人口比が決定的でマナも足りればArmageddonが発動する」
    テストは、時間ゲートの影響を受けないよう`minArmageddonTime: 0`
    を明示するよう更新した。
- `src/game/simulation.test.ts`：「敵AIが自発的に発動した奇跡も
  記録される」という既存テストは、試合開始0.1秒後というシナリオ
  のままではArmageddonがこのゲートでブロックされ火山にフォール
  スルーするようになったため、期待するイベント種別を`armageddon`
  から`volcano`へ更新した（このテスト自体の目的である「敵の自発的
  な奇跡もmatchEventsに記録される」という検証は変わらず成立する）。
- `npm run typecheck` / `npm run test -- --run`（237件）/
  `npm run build`がすべて成功。
- 放置シナリオ（敵AIのみで自律運転）を20回試行し、決着時間を
  比較：
  - 導入前（`plan/0044`時点）：平均137.5秒、中央値約113秒
  - 導入後：**平均230.6秒（3:50）、範囲192〜350秒**
    （全試行が180秒のゲート付近以上に収まり、分布のばらつきも
    自然になった）
  - `plan/0043`導入前（今回の一連の変更が入る前の元の状態）の
    平均108.8秒と比べ、決着時間はおよそ2倍以上に伸びた。

## 残作業

- 180秒という値はまだ仮の下限。ユーザーが提示した目標
  （通常戦10〜15分、早期決着5〜8分）に対しては、まだ短い側
  （実測の中心は3〜6分）。次にどこまで伸ばすかはプレイテストの
  結果を見て判断する。
- 人口比そのものの算出方法（`totalPopulation`の振れ幅の大きさ）
  自体は今回手を付けていない。今回は「早すぎる発動を止める下限」
  という形で対症療法的に対応したが、指標そのものの安定化は
  別の残課題として残っている。
- ユーザーが別途示した優先順位（64×64化とゲームテンポ→城vs拡張の
  トレードオフ→…）のうち、ここまでの一連の変更で「ゲームテンポ」
  側はかなり前進した。次にどれへ着手するかは改めて相談する。
